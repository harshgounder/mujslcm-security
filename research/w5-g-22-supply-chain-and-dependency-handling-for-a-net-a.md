# MUJ SLCM .NET Supply-Chain and Dependency Handling Report

## Executive Summary

This report answers the narrow question that the current campaign has not closed: how to enumerate, verify, monitor, and detect risks in a .NET application's NuGet, binary, frontend, theme, vendor, and build dependencies without turning a university exercise into unauthorized testing. The catalog is exhaustive for the distinct technique families and publicly documented tools that are relevant to this target. It is not a claim that every commercial SCA SKU in the market has been listed when its NuGet capability or terms were not publicly documented in the material reviewed.

- **Inventory Gap**: The campaign brief says npm and PyPI were checked, while NuGet, vendor assemblies, bundled Keen assets, and dependency-confusion exposure were not enumerated. The immediate decision is to obtain source or build artifacts under the signed scope letter, rather than infer a server-side graph from HTTP behavior.
- **Native Baseline**: Microsoft tooling can list direct and transitive NuGet packages, filter known-vulnerable packages, and emit console or JSON results; `--include-transitive` is not implicit in the vulnerability listing and must be deliberately included. [19] [19] [19] -> Make this the first low-cost, repeatable control.
- **Audit Source**: NuGet restore checks package use against vulnerability information supplied by audit sources; nuget.org's vulnerability data is described as coming from the GitHub Advisory Database, and restore emits NU1900-series findings for communication, severity, and audit-source conditions. [1] [1] -> Preserve restore logs and fail builds on policy-defined advisories.
- **Confusion Control**: Package Source Mapping lets a project declare which feed each package may restore from, but it applies to downloads during restore, install, and update and does not filter every metadata query. [37] -> Inspect and lint `nuget.config`; do not treat source mapping as a complete malicious-package detector.
- **Vendor Separation**: Keen's public documentation describes a Yarn or npm dependency and Gulp or Webpack build process, while Telerik documents a private authenticated NuGet feed for its ASP.NET MVC releases. [3] [9] -> Treat frontend theme components and server-side Telerik-class assemblies as two separate inventories.
- **Integrity Gate**: NuGet signatures use X.509 certificates, and `dotnet nuget verify` or `nuget verify` can verify signatures; signed packages protect integrity and origin claims but do not establish that a package is safe or free of known vulnerabilities. [35] -> Require verification and trusted-source policy, then perform independent vulnerability and behavior checks.
- **SBOM Pipeline**: CycloneDX for .NET creates a BOM containing project dependencies, Microsoft SBOM Tool creates SPDX 2.2 or 3.0 SBOMs, and Dependency-Track consumes and produces CycloneDX SBOM, VEX, and VDR records through a REST-friendly platform. [7] [40] [26] [26] -> Produce one build-time SBOM and retain it with the release artifact.
- **Black-Box Limit**: A public portal response can reveal framework clues, static asset names, hashes, and error behavior, but it cannot prove the complete server-side NuGet graph, private-feed provenance, loaded assembly set, or reachability of a vulnerable method. This is an inference from the boundary between package-analysis inputs and the supplied unauthenticated campaign facts, not a claim that the target is or is not vulnerable.
- **Authorization Boundary**: Passive retrieval of public pages and public static files, and offline analysis of supplied source or binaries, are suitable pre-authorization activities. Authenticated portal use, private-feed access, build or deployment inspection, runtime instrumentation, active dependency-confusion validation, fuzzing, or tests designed to exercise the observed error oracle require the signed scope letter and the two test accounts.

## Scope, Evidence, and Auditable Reasoning Summary

The target information in the brief is treated as sponsor-supplied campaign data: IIS 10, ASP.NET MVC 5.3, .NET Framework 4.7.4136.0, the two reported jQuery versions, Azure AS8075, Microsoft 365 identity, three Entra tenants, the transport and error observations, the GET-only policy, and the authorization gate. Those measurements are not re-performed here. The public corpus independently shows that the MUJ SLCM host presents a sign-in portal, but it does not publish a NuGet manifest or a component inventory. [44]

The reasoning chain is deliberately auditable rather than private chain-of-thought. First, identify what each technique requires as input. Native NuGet commands require a project, solution, restored assets, or package configuration; FOSSA documents `project.assets.json` and project files as dependency sources, while Trivy documents `*.deps.json`, `packages.config`, package props, and `packages.lock.json` for .NET and NuGet analysis. [22] [24] Second, compare those inputs with what an unauthenticated HTTP observer has: pages, headers, responses, and sometimes static files. Third, mark every conclusion that would require a missing artifact as an inference. Fourth, select the least intrusive tool that can close the specific evidence gap. Finally, impose authorization gates before any action that could access a private feed, authenticate, change state, execute a build, or intentionally test a package name.

The practical consequence is important. The supplied YSOD, error-size, method-policy, antiforgery-cookie, TLS, and header observations are useful application-security context, but they do not substitute for a dependency graph. They can justify prioritizing information-disclosure remediation and a careful artifact request. They cannot establish whether a NuGet package, Telerik component, Keen plugin, or vulnerable transitive library is present. Any statement below that relates to the target itself is therefore labelled as campaign input, public evidence, or inference.

## 1. Technique Universe for .NET Supply-Chain Assessment

A complete assessment is not just a CVE scan. It is a sequence from discovery to evidence preservation, matching, decision, and remediation. The table below separates the technique from the evidence it needs and the result that a defensible report should retain.

| Technique family | What it answers | Evidence needed | Detection counterpart and retained output |
|---|---|---|---|
| Source and manifest discovery | What packages and tools are declared? | `.sln`, `.csproj`, `packages.config`, `Directory.Packages.props`, `nuget.config`, CI files, `package.json`, npm or PyPI lock files | File inventory, path, repository commit, package manager, and hash |
| Resolved graph construction | What direct, transitive, build, runtime, and development dependencies actually resolve? | `project.assets.json`, `packages.lock.json`, `*.deps.json`, restored package cache, package props | Graph with parent edges, target framework, requested version, resolved version, and content hash; `dotnet package list --include-transitive` and `dotnet nuget why` are the native counterparts. [19] [1] |
| Component identity normalization | Are the same components represented consistently across manifests, DLLs, and SBOMs? | Package ID, version, PURL, assembly name, file hash, repository and publisher metadata | Canonical component records and deduplication decisions; CycloneDX and SPDX are suitable exchange formats. [7] [40] |
| Known-vulnerability matching | Does a component version have a public advisory? | Resolved version, ecosystem, advisory database, severity and affected range | NuGet Audit, OSV-Scanner, Trivy, Dependency-Check, and hosted SCA findings; preserve database date and advisory identifiers. [1] [20] [24] [8] |
| Reachability and exploitability | Is vulnerable code present in a reachable application path? | Source or IL, call graph, entry points, framework configuration, runtime evidence | Call graph or manual code-review evidence; a package-level CVE result alone is not proof of exploitability. | Package integrity and provenance | Was the package altered, and who signed or supplied it? | `.nupkg`, signature, timestamp, source URL, content hash, trusted root and signer policy | `nuget verify`, signature status, trusted signer decision, source mapping result, and hash comparison. [35] [33] |
| Dependency confusion and typosquatting | Could a private or internal package name resolve from an unintended public feed? | Internal package names, all feed URLs, feed priority, `nuget.config`, source mapping, restore logs | Mapping-policy result, unmapped-name exception, package-source decision, and safe local simulation. Do not publish or pull a candidate package against the university target. [37] |
| Malicious-package behavior | Does a package perform suspicious build or runtime behavior beyond known CVEs? | Package archive, `.nuspec`, build targets, content files, analyzers, scripts, binaries, network and process behavior in an isolated lab | Static behavior review, isolated sandbox telemetry, reputation and provenance evidence; a CVE scanner is not a malware detector. | License and notice compliance | What licenses and obligations apply to direct and transitive components? | Package metadata, license expression or file, notices, concluded license, distribution model | SPDX or CycloneDX license records, allow or deny policy, generated notice bundle; Microsoft SBOM Tool can populate license information through its component detection and ClearlyDefined integration. [40] |
| SBOM and VEX management | What was shipped, and which findings are not exploitable or not applicable? | Build artifact, component graph, release identity, VEX decision | CycloneDX or SPDX SBOM plus VEX or VDR; Dependency-Track documents SBOM, VEX, and VDR consumption and production. [26] [26] |
| Update and drift control | What changed between builds and what is stale? | Previous SBOM, lock file, manifest diff, release hash, advisory feed history | Pull request, policy decision, reproducible restore result, and release-to-release diff; Renovate and dotnet-outdated are update-oriented counterparts. [12] [41] |
| Deployed-artifact reconciliation | Does production match the approved build? | Approved SBOM, deployed DLLs, static assets, container or package hash, deployment record | Binary inventory and hash comparison; Dependency-Check's assembly analyzer can collect vendor, product, and version evidence from .NET DLL and EXE files. [45] |
| Frontend and theme inventory | Which JavaScript, CSS, fonts, widgets, and vendor bundles are actually served? | Public static files, source maps, build manifests, package locks, SRI hashes, release archive | Hash inventory, package-to-file mapping, duplicate-version findings, and license records; do not infer server-side Telerik use from a frontend visual similarity. |
| Cloud and identity dependency mapping | Which Azure, Entra, Microsoft 365, certificates, feeds, and CI identities are build or runtime dependencies? | Architecture diagrams, service connections, app registrations, deployment pipelines, secret references | Authorized configuration review and dependency graph; public DNS or response behavior cannot prove tenant ownership or trust relationships. |

The key decision is to run the techniques in that order. A vulnerability scan before graph construction creates false confidence, while a graph without source and integrity evidence cannot answer dependency confusion or malicious-package questions. The target's missing NuGet and vendor inventories should therefore be recorded as an evidence gap, not silently filled with product guesses.

## 5. Manual Method When the Tool Cannot See the Target

The manual method is an evidence-preservation procedure, not a request to probe the live portal. It is necessary because no external scanner can reliably infer an entire private server-side NuGet graph from a public MVC response. The public host can be used only for passive, authorized collection of public pages and static assets.

### 5.1 Build the evidence pack

Request, under the signed scope letter, a read-only export of the source or build pipeline containing the solution file, project files, `packages.config`, `Directory.Packages.props`, `nuget.config`, `packages.lock.json`, `project.assets.json`, `*.deps.json`, CI definitions, approved package feed list, and release artifact hashes. For legacy .NET Framework, also request the restored `packages` directory or an approved package-cache export, the `bin` directory, web configuration, MVC views, assembly binding redirects, and any vendor license or installation record. Do not ask for secrets, private keys, production database content, or live tokens.

For the frontend, request the Keen source archive or build manifest, `package.json`, npm or Yarn lock file, Gulp or Webpack configuration, generated bundle list, source maps if available, and license notices. The official Keen documentation makes the Yarn or npm plus Gulp or Webpack build chain a relevant evidence source. [3] The existence of a Keen build dependency does not prove that every plugin in the theme is shipped by MUJ; include only files actually present in the approved release.

### 5.2 Normalize and resolve locally

Create a read-only copy and record cryptographic hashes before analysis. Enumerate package IDs and versions from manifests and resolved assets; retain target framework and runtime or development classification. Use `dotnet package list --include-transitive --format json`, `dotnet nuget why`, and the native audit path. Where restore is necessary, use a disposable build environment with an allowlisted feed configuration. Do not connect a private feed from an unapproved machine, and do not let a default global NuGet configuration silently add an extra source.

For every component, retain the package ID, resolved version, parent path, PURL, source URL, content hash, signature status, license expression, repository metadata, and the files that caused the match. Generate CycloneDX and SPDX where possible. If the project cannot be restored, scan the supplied DLLs and archives separately and mark the result as binary evidence rather than a complete source graph.

### 5.3 Inspect the server and frontend boundaries separately

For server-side Telerik-class components, search project references, package folders, assembly metadata, binding redirects, MVC view helpers, namespaces, and vendor installation manifests. Telerik's own documentation says its official ASP.NET MVC releases and service packs are distributed through a private NuGet feed, and its NuGet setup requires an authenticated feed. [9] [50] That means a public static-file match is not enough to establish Telerik server use, and a private feed record is not enough to establish deployment in the current release.

For the Keen side, map each served JavaScript and CSS file to its source package or vendor archive by content hash, not only by filename. Record duplicate jQuery copies as separate assets, determine which one loads first in the approved page, and preserve the exact file hash. jQuery's public license page identifies the MIT license for projects referencing its license document. [10] This is a license and inventory fact, not evidence that the reported target versions are exploitable.

### 5.4 Review confusion and malicious-package exposure safely

The safe pre-authorization review is configuration-only: list package IDs that look internal, list all configured sources, compare them with Package Source Mapping, and check whether every internal pattern is pinned to an approved private feed. Review restore logs for unexpected source selection. Do not publish a package with an internal-looking name, do not attempt to make a production build choose a public candidate, and do not alter the target's feeds.

The safe malicious-package review is also offline: inspect the package archive, `.nuspec`, build targets, analyzers, content files, embedded binaries, and declared repository or publisher metadata in a sandbox disconnected from production. Any dynamic execution of package build or install behavior requires the signed letter and a disposable lab; it must not use the live portal, production credentials, or a university-wide CI runner.

## 6. Detection Counterpart: What to Detect After Inventory

Inventory is only useful if every observed condition has a detection and response counterpart. The following matrix turns a package list into a decision process.

| Inventory observation | Detection test | Acceptable evidence | Response decision |
|---|---|---|---|
| Direct package with advisory | Match exact version and affected range against NuGet Audit and an independent scanner | Advisory ID, source, database date, package path, severity, and fixed version | Patch, pin a safe version, or document a time-bound exception |
| Vulnerable transitive package | Trace the parent with `dotnet nuget why` and inspect whether the parent can be upgraded | Dependency path and test build result | Upgrade the closest controllable root; do not blindly override a transitive version |
| Package name appears on public and private feeds | Check source mapping and restore logs | `nuget.config`, mapping pattern, feed decision, and lock file | Fail restore when a package lacks an approved source mapping |
| Unsigned or untrusted package | Run signature verification and compare content hash | Signature result, timestamp, signer, root store and source | Reject or obtain an approved signer exception; signature is not a vulnerability waiver |
| Internal package name without mapping | Simulate resolution in an isolated local repository only | No public publication, no production restore, written authorization if dynamic validation is needed | Treat as a high-priority control gap until mapping and private-source ownership are documented |
| DLL found in release but absent from manifest | Reconcile binary inventory with approved SBOM and release record | File hash, assembly metadata, deployment manifest and build provenance | Investigate drift or untracked manual deployment |
| Frontend file has a vendor signature but no source record | Compare hash, source map, package lock and license notice | Exact static-file hash and source artifact | Add it to the SBOM or remove it from the approved build |
| License metadata is missing or contradictory | Compare package metadata, license expression, notice file and vendor terms | SPDX or CycloneDX license record and legal review | Block release or create a documented legal exception |
| Advisory exists but reachability is unknown | Perform source or IL call-graph review, then manual confirmation | Reachability path, entry point, configuration and version | Prioritize confirmed reachable cases; do not call an unreviewed package safe |
| SBOM differs from deployed artifact | Compare release SBOM to deployed DLL and static-file hashes | Signed build record and artifact hash comparison | Roll back, rebuild, or record why the deployed artifact is approved |

The important negative finding is that no single tool supplies all rows. Native NuGet audit is strong on current advisory matching. Signatures and source mapping are strong on restore integrity. SBOM tools are strong on inventory exchange. Binary analyzers are useful when project files are unavailable. Malware and reachability require separate evidence and human review.

## 7. No-Tool Gaps and Build Candidates

The following gaps explain why the campaign remains PARTIAL. They are not accusations against the target; they are statements about what the current evidence cannot establish.

| No-tool or evidence gap | Why ordinary scanning cannot close it | Build candidate | Priority and authorization |
|---|---|---|---|
| Complete server-side NuGet graph from unauthenticated HTTP | The graph exists in source, restored assets, packages, or deployed binaries, not necessarily in public responses | Read-only artifact-ingestion job for project files, assets, packages, and DLLs; emit CycloneDX plus JSON | High; source or artifact handoff under the signed letter |
| Legacy .NET Framework packages versus modern SDK metadata | A project may use `packages.config`, binding redirects, copied DLLs, or manual references that a modern project command does not see | Dual parser for `packages.config`, project references, `project.assets.json`, `packages.lock.json`, and binary metadata | High; offline analysis can start as soon as artifacts are supplied |
| Telerik-class server component identity | A private vendor feed, DLL namespace, view helper, or copied assembly may not be visible in public static files | Assembly and MVC-view fingerprinting with hash and version evidence, cross-checked against approved vendor records | High; artifact review under the letter, no live feed probing |
| Keen bundle completeness | Theme build tooling can include optional plugins, while the deployed bundle may be minified or renamed | Static asset manifest, hash-to-package mapper, source-map parser, duplicate-library detector, license collector | High; public static files may be passively collected pre-authorization if allowed |
| Dependency-confusion exposure | It depends on private package names, source order, credentials, and restore policy, none of which public HTTP proves | `nuget.config` linter that requires a mapping for every internal namespace and rejects ambiguous feeds | High; configuration review pre-auth if supplied; dynamic validation requires letter |
| Malicious package behavior | CVE databases do not detect every build script, analyzer, obfuscated payload, or publisher compromise | Offline archive scanner plus isolated behavior sandbox with network and process telemetry | Medium to high; static review pre-auth on supplied archives, execution only under letter in a disposable lab |
| Reachability and exploitability | A vulnerable package may be unused, or a vulnerable method may be reachable only through a path not represented in a package list | Optional call-graph and IL analysis, followed by source review and a test-account regression test | Medium; authenticated testing requires letter and test accounts |
| Deployed-versus-approved drift | The live host may contain a manually copied DLL or static file that never entered the CI SBOM | Release hash attestation and deployment reconciliation job | High; production comparison requires owner authorization and should avoid state changes |
| Unified npm, PyPI, NuGet, and binary record | Separate ecosystem checks cannot show one release-level component set | CycloneDX or SPDX merger keyed by PURL, hash, and release ID, with VEX support | High; local build-side work is safe pre-auth |
| Feed and identity ownership | Public Azure, Microsoft 365, or Entra clues do not establish who can publish packages or change CI | Authorized CI and feed control matrix with owner, role, MFA, approval, and audit-log evidence | High; requires owner-provided configuration, not public probing |
| Public black-box version inference | Headers, error pages, and static names can be stale, customized, or shared across versions | Confidence-scored fingerprinting that never elevates a guess to an SBOM component without artifact corroboration | Medium; passive collection only pre-auth |

The highest-value build candidate is therefore not a new scanner. It is a small evidence pipeline that accepts approved source, package, binary, and static-asset inputs; emits a canonical SBOM; runs two independent matching paths; and records provenance, source mapping, signature status, and release hashes. That closes the campaign's actual missing evidence instead of adding another dashboard.

## 8. Authorization and Safe Operating Boundary

The campaign brief says the aggressive phase is gated by a signed scope letter and two test accounts. That is the correct boundary. The table below is an explicit operating rule for a university security club.

| Activity | Pre-authorization status | Conditions if authorization is required |
|---|---|---|
| Read the public MUJ portal landing page and publicly linked static files | Generally safe if rate-limited and permitted by the site owner | Stop if a file is not public or if collection terms prohibit it |
| Record public TLS, headers, status codes, page sizes, and visible framework clues | Passive and generally safe, but do not expand into endpoint discovery | Use a low request rate and retain timestamps; do not repeat error triggers merely to increase confidence |
| Analyze source, package archives, DLLs, SBOMs, or static files supplied by the owner | Safe offline | Preserve hashes and do not execute untrusted build scripts on a production or club workstation |
| Query public package registries for already-known package IDs and versions | Safe as ordinary public research | Do not use private credentials or restore an unapproved project from an unknown feed |
| Run local NuGet Audit, CycloneDX, Microsoft SBOM Tool, Trivy, Dependency-Check, OSV-Scanner, or license inventory | Safe on supplied artifacts in an isolated environment | Pin tool versions and document databases; do not permit builds to contact production services |
| Access authenticated portal functions or test accounts | Not pre-authorized | Signed scope letter, named accounts, rate limits, test windows, and owner contact required |
| Exercise the observed `enc` error oracle, vary methods, enumerate paths, or test trust headers | Not pre-authorized | Signed scope letter, explicit test cases, two test accounts where applicable, and stop conditions required |
| Inspect private NuGet feeds, CI service connections, Entra or Microsoft 365 configuration, or deployment logs | Not pre-authorized | Owner-provided read-only export or explicit access in the letter; never reuse production tokens |
| Publish or attempt to resolve a dependency-confusion candidate | Prohibited without explicit written authorization and an isolated disposable repository | Never point a candidate at the live target or production CI; use an owner-controlled canary process only |
| Execute package install/build scripts or dynamic malware tests | Not pre-authorized | Disposable isolated lab, signed scope, no production credentials, and explicit cleanup plan |

The observed verbose error pages and transport weaknesses may matter to the wider web-application report, but they do not justify bypassing the dependency evidence boundary. A security club can make substantial progress before authorization by building the offline parser, SBOM merger, mapping linter, and license report. The live portal should not be used as a substitute for a source or artifact handoff.

## Synthesis

The tools divide into three different mechanisms. Native NuGet controls operate at restore time: they know the declared graph, configured sources, audit data, signatures, and lock state. SBOM tools operate at build or artifact time: they create a portable description of what the project or artifact contains. Hosted SCA platforms operate at governance time: they add policy, dashboards, private-feed handling, identity, license workflow, and sometimes reachability or behavioral signals. Confusing these mechanisms creates the central failure mode in this campaign: using a restore-time or SBOM tool as if it could prove the contents of a remote live server.

The trade-off is also clear. Native commands are cheap, reproducible, and best aligned with .NET, but they require project or restored inputs and do not by themselves analyze malicious behavior. Dependency-Check and Trivy broaden the fallback to DLLs and directories, but binary evidence is less precise than a locked source graph. Dependency-Track and commercial platforms preserve history and policy decisions, but they add hosting, data-sharing, licensing, and credential questions. This is why the recommended sequence is artifact first, SBOM second, independent matching third, and governance fourth.

The most important divergence concerns integrity versus safety. A signed package can provide authenticity and tamper evidence, but a signed vulnerable or malicious package remains a risk. Package Source Mapping can stop an unintended feed choice, but it does not inspect every metadata query and it does not prove the chosen package is benign. Vulnerability matching can identify known advisories, but absence of a finding is not proof of reachability safety, clean behavior, or complete inventory. Each control closes a different failure mode and must be retained as separate evidence.

The target-specific conclusion follows from that comparison. The campaign's current PARTIAL status is justified because the missing inputs are exactly the inputs required by the strongest controls: NuGet manifests and resolved assets, private-feed policy, vendor DLLs, Keen build metadata, and a release-to-deployment comparison. The fastest path to a high-confidence result is not more unauthenticated probing. It is a signed, read-only artifact request followed by a local pipeline using native NuGet Audit, source mapping and signature checks, CycloneDX or SPDX generation, two independent scanners, and a manual review of vendor and frontend evidence.

## VERDICT

**Overall confidence in the technique universe and tool catalog: High.** The core capabilities, formats, source-mapping limits, signature behavior, .NET/NuGet input types, and SBOM functions are grounded in official Microsoft, OWASP, vendor, or project documentation cited above. The catalog distinguishes verified capability from a source excerpt that did not state a license, hosting model, or NuGet entitlement.

**Confidence in the MUJ SLCM dependency inventory: Low.** Public information and the supplied unauthenticated measurements do not establish the deployed NuGet graph, private-feed configuration, Telerik-class server component set, Keen plugin set, package signatures, or reachability. The reported target versions and live observations are accepted as campaign inputs, not independently verified public facts.

**Risk-management verdict: Campaign remains PARTIAL, with a high-priority evidence gap rather than a confirmed package vulnerability.** Close the gap with an authorized read-only source/build/artifact export. Run native graph and audit controls first, then generate a signed SBOM, cross-check with binary and filesystem scanners, review source mapping and signatures, and reconcile the approved SBOM with deployed hashes. No dependency-confusion publication, private-feed probing, authenticated portal testing, error-oracle exercise, package-script execution, or runtime instrumentation should occur before the signed scope letter and the two test accounts are in place.
