# MUJ SLCM Fix Verification and Retest Loop

## Executive Insights

- **Closure Standard**: The campaign has ten findings but no defined acceptance evidence. OWASP ASVS says a verifier should make scope clear, summarize requirements checked, document exceptions, disclose repeatable methods, and retain work papers, screenshots, scripts, and testing logs [13]. -> Adopt one finding record and one evidence pack per finding before calling any item closed.
- **Safety Boundary**: ZAP's Baseline mode is documented as spidering plus passive analysis without actual attacks and is intended for CI/CD, including production sites [14]. PortSwigger also warns users not to use Burp against systems without owner authorization [51]. -> Pre-authorization work should stay offline or limited to evidence already supplied; all live probing beyond ordinary use requires the signed scope letter.
- **Coverage Reality**: WSTG covers configuration, authentication, authorization, session, injection, error handling, cryptography, client-side, API, and reporting categories [9]. ASVS cautions that automated DAST and SAST cannot fully verify complex business logic or access-control requirements [13]. -> Use scanners as detectors and accelerators, not as the closure authority.
- **Error Oracle Discipline**: The supplied `enc` measurements show three response classes, but they do not by themselves prove a padding oracle, decryption weakness, or exploitable cryptographic flaw. -> Retest response equivalence and information disclosure first, then require code review or a safe test fixture before making a cryptographic conclusion.
- **Targeted Regression**: The supplied baseline includes verbose YSODs, two error-page families, a non-Secure antiforgery cookie, TLS 1.0 availability, missing HSTS, and a three-stage `enc` response difference. -> Build a deterministic assertion set for status, headers, cookies, content type, body fingerprints, and exception leakage rather than relying on body length alone.
- **Authentication Gap**: The campaign never authenticated, so it cannot close authenticated authorization, session, CSRF mutation, or role-separation findings. -> Reserve those cases for the signed scope letter and the two test accounts, with explicit test data ownership and stop conditions.
- **Tool Complementarity**: Nuclei supplies YAML-driven checks and JSON, JSONL, SARIF, Markdown, and PDF exports [21]. Retire.js detects JavaScript libraries that may be absent from package manifests and can emit CycloneDX SBOMs [38]. -> Pair network and browser detection with source, dependency, and deployed-artifact verification.
- **Build Priority**: The highest-value missing capability is not another scanner. It is a safe, repeatable runner that binds a finding to a fixed request, expected result, deployment identifier, redacted evidence, and an approval state. -> Treat the retest harness and evidence schema as a P0 engineering deliverable.

## Scope, Safety, and Transparent Reasoning Summary

This report addresses fix verification and the retest loop for the MUJ SLCM portal at `https://mujslcm.jaipur.manipal.edu/Home/Index`, whose public landing page identifies it as the MUJ portal [52]. The IIS, ASP.NET MVC, .NET Framework, jQuery, Azure, Microsoft 365, and Entra details, as well as the live observations dated 2026-09-13, are treated as engagement-provided facts. I have not independently re-probed the target in this report.

The requested `cot_explicit` requirement is handled as an auditable reasoning record, not private chain-of-thought. The reasoning is reproducible: observation -> security mechanism -> verification decision -> evidence needed. NIST SP 800-115 frames technical testing as planning and conducting tests, analyzing findings, and developing mitigation strategies, while also emphasizing the benefits and limitations of particular techniques [11]. ASVS similarly requires the verifier to explain what and how was tested, root cause, remediation guidance, severity, and business impact [12].

| Boundary | Safe before authorization | Requires signed scope letter | Requires letter plus two test accounts |
|---|---|---|---|
| Offline research | Read public documentation, source repositories, licenses, and previously supplied captures. Build the harness against a local fixture or staging copy. | None | None |
| Live passive checks | Do not treat a live request as automatically safe merely because it uses GET. Owner-published testing permission is the correct basis. | Any live scan or repeated request outside normal user activity, including headers, TLS, port, route, and error checks. | None, but accounts are not needed only when the test is truly unauthenticated and explicitly in scope. |
| Active HTTP checks | None against the live portal before authorization. | Method variation, malformed-input classes, host-header variants, route discovery, active DAST, fuzzing, and repeated differential requests. | Authenticated DAST, CSRF mutation tests, session tests, authorization or IDOR tests, and any action that changes test data. |
| Source and build checks | Local code, configuration, dependency, and SBOM scans where the university supplies the artifact or repository. | Deployment confirmation and production artifact comparison. | Authentication and authorization fixtures must use the supplied accounts and approved records only. |
| Stop conditions | Stop if a live action is requested without written authorization. | Stop on data mutation, unexpected account access, service degradation, rate-limit signals, or out-of-scope hostnames. | Stop on cross-account visibility, real student data, account lockout, or any irreversible action. |

The engagement input states that 443 is the only reachable port, four triggers produce verbose YSODs with `customErrors` off, MVC antiforgery is enforced, the antiforgery cookie is HttpOnly but not Secure, `trace.axd` returns 403, `elmah.axd` returns 404, method handling is GET-only with 411/404 results for other methods, the `enc` parameter has three response classes, two error-page families exist, trust-based bypass attempts were clean, and no authentication occurred. These are the initial evidence baseline, not closure evidence. The report therefore uses them as assertions to re-run only after authorization.

The reasoning consequence is important. A clean Host header or absolute-URI test is a useful negative-control result, but it does not prove every proxy or future deployment path is safe. A 403 or 404 is evidence about the tested unauthenticated path, not proof that the same resource is inaccessible to every role. A smaller error page is not proof that sensitive information is gone. A scanner finding disappearing is not proof that the code path, deployed artifact, and business control are all fixed.

## What Counts as a Closed Finding

A finding should move through explicit states rather than a single fixed/not-fixed flag. ASVS says the scope should state what was included and why excluded requirements were omitted, and that testing methods should be disclosed and ideally repeatable [13]. Its evidence examples include work papers, screenshots, scripts, and testing logs [13].

| State | Required decision | Minimum evidence | Owner |
|---|---|---|---|
| Open | The original observation is reproducible or accepted as a supplied baseline. | Original request class, endpoint, response fingerprint, date, scope, severity, and affected build if known. | Security club plus university owner |
| Fix claimed | A remediation exists and is deployed to a named environment. | Change or release identifier, deploy timestamp, configuration/code diff summary, and rollback reference. | Development/operations |
| Targeted retest | The original assertion is repeated with the same preconditions and a safe negative control. | Redacted request/response, status, headers, cookie attributes, body hash, body size, tool version, and runner log. | Tester |
| Regression pass | Related controls and known clean negative controls still behave correctly. | Regression result set, no unexpected mutations, and comparison against the approved baseline. | Tester and application owner |
| Accepted closure | The university accepts residual risk and evidence. | Finding record links, reviewer identity, date, residual risk, exceptions, and approval. | University security owner |
| Reopened | The fix is absent, incomplete, bypassable, or unverified in the deployed artifact. | New failing assertion and preserved previous evidence. | Security owner |

**Decision rule:** a finding is not closed merely because a tool reports no issue. ASVS explicitly says that merely running an automated tool without thorough testing is insufficient and that each requirement must be verifiably tested [13]. The closure pack should preserve both positive and negative controls. A positive control is the old observation in a lab fixture or previously captured evidence; a negative control is the expected safe behavior after the fix. Do not recreate a harmful condition on production just to produce a positive control.

The key detection-versus-verification distinction is deliberate. Detection asks whether a pattern is present. Verification asks whether the same control now rejects, normalizes, or safely handles the condition, while related controls remain intact. The ASVS discussion says automated tools can find some issues but that manual tests, source analysis, and application-specific unit or integration tests may be needed [13].

## Manual Method Where No Tool Is Sufficient

Some of this campaign is inherently application-specific. The manual method should be written as a controlled test case, not as ad hoc browsing.

1. **Freeze the finding contract.** For each finding, record the exact URL, method, authentication state, approved input class, expected status, expected header and cookie properties, response fingerprint, and a non-destructive stop rule. The original four YSOD triggers and the three `enc` input classes become named fixtures, not improvisational payloads.
2. **Capture a clean baseline.** Use a browser or approved proxy to capture one known-good request and response. Redact cookies, authorization headers, antiforgery values, student identifiers, and tokens. Record status, `Location`, content type, selected security headers, cookie attributes, body size, and a cryptographic body hash. Body size alone is not a sufficient assertion because the engagement already has two page families.
3. **Use semantic comparison.** Compare status and content type first, then stable headers, cookie flags, error-page fingerprint, and absence of stack-trace markers. Ignore dynamic timestamps, correlation IDs, and nonce values through a documented normalization rule. Preserve the unredacted evidence only in the university-approved vault.
4. **Test the negative control.** The fixed build should produce the approved generic behavior for each trigger. The negative control must not alter data, send notifications, change enrollment, or affect another account. If the only way to exercise the case would mutate state, use a local fixture or a staging copy.
5. **Test the related control.** After an error-handling fix, verify normal GET behavior still works. After a method-policy fix, verify the intended GET request still works and disallowed methods do not mutate state. After an antiforgery change, verify both valid-token success and invalid-token rejection using a test account.
6. **Correlate with server evidence.** Where the application owner can provide logs, match the request ID and time to a server-side event that records the exception without returning the exception to the user. Do not require the application to log secrets or raw tokens.
7. **Record a decision.** The tester writes Pass, Fail, Blocked, or Not Applicable with a sentence explaining why. The application owner records the deployment identifier and the university security owner records acceptance.

This method has no safe automated substitute for business meaning. ASVS says application-specific tests similar to unit and integration tests may be needed [13]. That is especially important for authorization and role separation, which have not been tested because the campaign never authenticated.

## Detection Counterparts and Evidence Pairing

Detection should have a defined counterpart. The same technique that found a condition is often not the best technique to prove its remediation.

| Detector result | Verification counterpart | Why the pair matters |
|---|---|---|
| DAST flags verbose error | Manual trigger replay plus source/config review | A scanner may detect a marker, but only the owner can confirm remote exception suppression and server-side logging. |
| Header scanner flags missing HSTS or cookie attribute | Raw response capture from the exact deployed host | Header tools can be affected by redirects, paths, proxy layers, or cached responses. |
| TLS scanner reports TLS 1.0 | Second TLS scanner plus written policy | A single scanner can report capability differently depending on handshake options; two machine-readable outputs make the closure reviewable. |
| Retire.js flags jQuery | Deployed asset hash and browser network capture | A source fix can leave a stale CDN, bundle, or cached asset in production. |
| SAST flags unsafe redirect or exception handling | Code review plus authorized end-to-end request | A rule may be syntactically correct while the live route is protected by another layer, or the reverse. |
| API fuzzer finds a server error | Replay log plus minimized safe case in a fixture | Large fuzz campaigns are not suitable closure evidence until reduced to a deterministic, non-destructive test. |
| Authenticated scanner reports access-control issue | Two-account manual role matrix | Automated crawling often cannot know which student record should be visible to which account. |
| Evidence platform shows a finding closed | Human acceptance record | Lifecycle status is metadata, not proof of a technical control. |

DefectDojo is useful here because it is intended to orchestrate testing, vulnerability tracking, deduplication, remediation, and reporting [6], and its reimport documentation specifically warns that unstable identifiers can close old findings and create new ones when minor attributes change [32]. The university should use a stable finding key based on the control and endpoint, not response length or line number alone.

## BUILD CANDIDATES

The build candidates below are deliberately modest. They turn the existing reaudit script into a controlled verification product without creating a general-purpose attack framework.

| Priority | Candidate | Minimum design | Exit criterion |
|---|---|---|---|
| P0 | ReTestSpec | YAML or JSON fields for finding ID, endpoint, method, input class, auth state, expected status, allowed headers, cookie assertions, body markers, normalization rules, rate limit, and stop condition. | Every one of the ten findings has a versioned test case that can run against a local fixture. |
| P0 | Safe HTTP runner | Explicit host allowlist, method allowlist, request cap, delay, timeout, no-follow-redirect option, no mutation by default, secret redaction, and emergency stop. | A dry run produces no live request; an authorized run cannot leave the allowlist. |
| P0 | Response fingerprint engine | Compare status, content type, selected headers, cookie flags, stable body hash, body size, and disclosure markers while ignoring documented dynamic fields. | The runner correctly distinguishes the MVC and IIS families without declaring a size-only oracle. |
| P0 | Evidence packager | Bundle redacted request/response, tool version, runner version, timestamp, target, source IP, deployment ID, test case hash, result, and reviewer. | A reviewer can reproduce the decision from the pack without receiving secrets. |
| P1 | Two-account auth fixture | Store account references outside code, isolate sessions, map role and owned canary record, and assert no cross-account data. | CSRF, session, and authorization tests run only on approved canaries and fail closed on missing fixtures. |
| P1 | ASP.NET error regression pack | Local test routes that throw representative exceptions, test `customErrors`, verify generic responses, and verify diagnostic logs without returning details. | MUJ-01, MUJ-02, and MUJ-06 have deterministic local and authorized-live assertions. |
| P1 | TLS/header snapshot | Run pinned testssl.sh and SSLyze versions, capture JSON/CSV, and compare protocol/header policy against an approved manifest. | TLS and HSTS results are diffable and policy-linked, not merely scanner-colored. |
| P1 | Dependency/deployed-asset manifest | Generate CycloneDX for .NET and JavaScript, record script content hashes, and compare repository, build, and live manifests. | MUJ-09 has evidence that the deployed scripts match the approved build. |
| P2 | SARIF/DefectDojo adapter | Normalize tool identifiers, stable endpoint/control keys, import/reimport rules, and finding lifecycle states. | Reimport does not create duplicates or silently close a changed finding. |
| P2 | CI policy gate | Run passive checks on every build, require manual approval for production retests, and fail on unreviewed regressions. | A clean build cannot bypass evidence or deploy without a recorded security result. |

The design should deliberately avoid a generic exploit-payload library. The requested use case is verification of known controls, so fixtures should be named by finding and input class, minimized, reviewed, and safe by default. That design also makes the club's work easier to transfer to university operations.

## Synthesis: What the Tooling Can and Cannot Prove

The main tension is between breadth and meaning. ZAP, Nuclei, Nikto, testssl.sh, SSLyze, Trivy, and Dependency-Check provide broad repeatable detection. Their strengths are speed, structured output, and regression comparison. Their trade-off is that they operate on observable patterns and configured rules. They do not know whether a particular Student record belongs to account A, whether a parent is allowed to view a grade, or whether a cryptographic error difference is exploitable.

A second tension is between no-auth coverage and authenticated assurance. The campaign's unauthenticated evidence is useful for headers, TLS, public error behavior, and public diagnostic exposure. It cannot close session, CSRF mutation, or authorization findings. Burp and ZAP can automate login contexts [16][14], while Newman and Playwright can make a known workflow repeatable [29][26]. The trade-off is credential handling and the risk of state mutation, which is why the two test accounts and signed scope letter are controls, not inconveniences.

A third tension is between response normalization and security signal. A fix may intentionally make multiple errors look alike, but an over-aggressive comparator can hide a new regression. The right mechanism is a layered assertion: policy outcome, status, content type, selected headers, cookie attributes, disclosure markers, body fingerprint, and server log correlation. The `enc` three-stage result is the clearest example: normalize external error behavior, preserve useful internal diagnostics, and separately review the cryptographic implementation. This is an inference from the supplied measurements, not a claim that the portal has a padding oracle.

The evidence systems solve a different problem. DefectDojo can import, deduplicate, reimport, and track findings [66]. Dependency-Track can receive CycloneDX through its REST API, CI plugins, or web interface and continuously re-analyze components [31][65]. GitHub can accept SARIF generated outside GitHub [33]. None of these systems determines technical truth or university acceptance. They preserve the chain from detector to artifact to reviewer; the club still needs a control-specific test and an authorized scope.

The resulting operating model is therefore three-layered: local source and dependency verification on every build; authorized non-attacking external baseline checks after deployment; and targeted authenticated/manual verification for controls whose meaning depends on identity or state. That model is more defensible than buying another broad scanner because it directly addresses the campaign's stated absence: no retest harness and no defined closure evidence.

## Safe Operating Rules for the University Security Club

1. Before the letter, work offline: analyze public documentation, supplied captures, public repositories, local copies, test fixtures, and tool licensing. Do not repeat live scans or malformed-input tests merely because the endpoint is public.
2. The scope letter should name the exact hostname, permitted IPs, dates and times, source addresses, request budget, methods, authenticated routes, test accounts, data exclusions, notification contact, stop conditions, and evidence-retention rules.
3. Start with a dry run and local fixture. Then run the least active authorized control: a narrow ZAP Baseline or header/TLS snapshot, not an active scan or fuzz campaign. ZAP documents Baseline as non-attacking [14], but authorization is still required by the owner boundary.
4. Keep all credentials, cookies, antiforgery tokens, and personal data out of issue comments and source control. Redact before importing into DefectDojo, GitHub, or any hosted system.
5. Require the university application owner to supply the deployment ID and server-side correlation evidence. A tester should not infer production deployment from a changed page size.
6. Close only when the finding record, targeted retest, regression result, deployment identity, and reviewer acceptance are linked. If any element is missing, use Blocked or Fix claimed, not Closed.

**Verdict: CAMPAIGN STATUS TO BEAT remains ABSENT.** The available facts show a useful initial non-destructive baseline, but they do not yet constitute a retest harness or a university-acceptable closure system. The acceptance decision belongs to the university security owner, not to a scanner, a script exit code, or an unreviewed finding import.
