# MUJ Register Numbers: Predictability Without Safe Enumerability

## Executive Summary

- **Confirmed Username Derivation**: MUJ's own SLCM FAQ publishes the login construction `name.registration-number` and illustrates it with `garv.2506040062`; it also says the password is "as per official outlook ID" [1]. This is the report's strongest finding: a register number is not merely an academic identifier, but one component of a predictable SLCM username. **Inference:** public knowledge of a person's name and register number can therefore reduce the uncertainty involved in identifying that person's login name. MUJ should treat both fields as public identifiers rather than authentication secrets.

- **No Verified Digit Decoder**: Neither the FAQ nor MUJ's first-year registration guide explains what `25`, `06`, `04`, or `0062` means. The guide describes "Registration No. (Generated by MUJ)" as a non-editable field populated from admission information [2], but provides no batch, stream, campus, or sequence legend. **Inference:** `25` may resemble a year and `0062` may resemble a zero-padded sequence, but publishing either interpretation as fact would exceed the evidence.

- **Structural Predictability Exceeds Semantic Predictability**: The official example establishes a ten-digit, decimal-looking identifier and a deterministic username separator [1]. **Inference:** the format is structurally predictable, while the validity of neighboring values and the meaning of each field remain unverified. This distinction matters: a predictable-looking number does not prove that production accounts can be enumerated.

- **Confirmed Public Exposure Is Narrow but Material**: A full example is indexed in an official MUJ PDF, while the onboarding guide publicly documents the existence and sensitivity of the registration-number field [1][2]. This review did not verify bulk MUJ register-number lists in public circulars, result PDFs, placement pages, or LinkedIn profiles. That negative result is not proof of absence; it means those channels should be monitored, not asserted as currently exposed.

- **Sensitive Object Surface Is Publicly Mappable**: A public Chrome-extension manifest names MUJ SLCM pages for attendance summaries, internal marks, and grades [6]. Its code reads attendance counts, marks, credits, and grades from the rendered page to calculate absence allowances, totals, and semester GPA [10]. This proves the existence and sensitivity of the page categories, not an IDOR vulnerability.

- **IDOR Risk Depends on Authorization, Not Number Secrecy**: OWASP defines IDOR as access or modification of objects through exposed identifiers when object-level access checks are missing [9]. It recommends access checks for every object and every access attempt, with random identifiers only as defense in depth [9]. **Inference:** register-number predictability would increase impact only if a MUJ endpoint incorrectly trusted a supplied identifier instead of the authenticated session.

- **Credential Attacks Are the More Direct Consequence**: OWASP defines credential stuffing as automated use of username/password pairs stolen elsewhere [3], recommends MFA [3], and warns that login, reset, and recovery responses must not disclose whether an account exists [12]. **Inference:** because MUJ publishes a username formula and relates the password to the Outlook identity, the login and recovery controls deserve higher-priority review than speculative digit decoding.

- **Defensive Validation Must Use Synthetic Accounts**: The club should not test neighboring identifiers, submit guessed usernames, alter object references, or test passwords against production. The safe path is a written-scope assessment using test tenants and synthetic students, with MUJ personnel supplying known-positive and known-negative cases. NIST calls for controls against online guessing and permits bot detection, progressive delays, and adaptive authentication signals [5].

**Decision-ready insight:** The evidence supports a **high-priority identity and authorization review**, but it does not support claims that the ten digits have been decoded, that production accounts are enumerable, or that MUJ has an IDOR.

## Scope, Safety, and Evidence Standard

This report uses only public university documents, public GitHub repositories, public standards, and public identity metadata. It did not authenticate to SLCM, submit a password-reset request, generate candidate register-number ranges, inspect another student's records, or probe live parameters. The example `2506040062` is retained only because MUJ itself publishes it in an official FAQ and the user supplied it in the research question [1]. No additional student identifiers are reproduced.

The technology description in the brief - ASP.NET MVC 5.3, .NET Framework 4.x, IIS 10, Akamai, and Microsoft 365 identity - is treated as an input assumption unless independently supported below. Public Microsoft OpenID metadata exists for the `muj.manipal.edu` domain and identifies Microsoft login endpoints [14]. The official FAQ independently refers to an "official outlook ID" [1]. Those sources support the Microsoft identity relationship, but they do not establish every asserted framework version, patch level, Akamai policy, or internal trust boundary.

The report applies three evidence labels:

| Label | Meaning | Permitted conclusion |
|---|---|---|
| **Confirmed** | Directly stated in an official document or visible in public source code | May be stated as fact with a citation |
| **Inference** | A bounded interpretation supported by confirmed observations | Must be labeled and must not be presented as verified architecture or behavior |
| **Unknown** | Public evidence is absent, ambiguous, or insufficient | Must not be filled with a guess |

The requested private chain-of-thought cannot be provided. Instead, this report supplies a reproducible reasoning audit: evidence, alternative explanations, confidence, and the decision each finding supports. This is more useful for peer review because another club member can independently check each cited source without receiving hidden internal deliberation.

A crucial scope distinction is MUJ versus other Manipal SLCM deployments. For example, a separate public scraper references `https://slcm.manipal.edu/loginForm.aspx` and `GradeSheet.aspx`, not the MUJ Jaipur host [15]. Another archived project describes a scraping API for "SLcM Manipal" [16]. These repositories may illustrate the wider ecosystem, but their routes, CAPTCHA behavior, credentials, and object models must not be attributed to `mujslcm.jaipur.manipal.edu` without MUJ-specific evidence.

**Decision-ready insight:** Use only MUJ-host-specific evidence for findings about MUJ. Treat code for MAHE or other Manipal portals as comparative context, not proof.

## What `2506040062` Does and Does Not Reveal

The official FAQ establishes two facts. First, the SLCM registration link is `https://mujslcm.jaipur.manipal.edu/` [1]. Second, it specifies `Username: name.registration number`, gives `garv.2506040062` as the example, and relates the password to the official Outlook ID [1]. The FAQ does not explain any digit boundary.

MUJ's first-year onboarding guide adds context. It calls SLCM a "one-stop platform" for academic information [2], says students log in at the MUJ SLCM URL using credentials sent by Admissions to their personal Gmail account [2], and describes the registration number as generated by MUJ and non-editable [2]. The same profile area includes student name, academic year, program or branch, date of joining, date of birth, gender, mobile number, email, and year of admission [2]. The presence of both "Registration No." and "Year of Admission" as separate fields does not prove that the year is or is not encoded in the number.

### Evidence-constrained decomposition

| Characters | Visible value | Confirmed meaning | Plausible inference | Confidence | Why the inference is limited |
|---|---:|---|---|---|---|
| 1-2 | `25` | Unknown | **Inference:** possible admission or cohort year | Low | One example cannot distinguish a year from a campus, school, system, or allocation code |
| 3-4 | `06` | Unknown | **Inference:** possible institution, campus, school, or program-family code | Very low | No second campus or program example is available for comparison |
| 5-6 | `04` | Unknown | **Inference:** possible stream, branch, intake, or subdivision code | Very low | MUJ publishes no codebook, and the student's program is not established by the FAQ |
| 7-10 | `0062` | Unknown | **Inference:** possible zero-padded serial or admission sequence | Low | Leading zeroes look sequential, but could also represent a random or composite allocation field |
| Whole value | `2506040062` | MUJ registration number used in an official username example | **Inference:** fixed-width numeric format for at least this onboarding cohort | Medium | A single example cannot establish all historical or program-specific formats |

No public evidence supports assigning "campus" specifically to `06`, "stream" specifically to `04`, or "batch" definitively to `25`. Campus encoding is especially difficult to infer because the document and host are already Jaipur-specific. A field that is constant within MUJ could denote campus, institution, system version, or nothing of the sort.

### Predictability assessment

| Dimension | Assessment | Basis | Security meaning |
|---|---|---|---|
| Length and character set | Confirmed for the example: ten decimal digits | Official FAQ [1] | Reduces format uncertainty |
| Username construction | Confirmed: name plus period plus registration number | Official FAQ [1] | Enables deterministic derivation when both components are known |
| Field semantics | Unknown | No official legend in the FAQ or onboarding guide [1][2] | Prevents a reliable batch/stream/campus decoder |
| Neighbor validity | Unknown | No authorized sampling or bulk official list | No basis for claiming sequential live accounts |
| Historical stability | Unknown | Only one authoritative example | The format may vary by year, program, or enrollment type |
| Check digit or validation rule | Unknown | No documentation | Candidate syntax cannot be equated with an assigned ID |

**Inference:** predictability is therefore **high at the syntax and username-composition layers, but low at the enrollment-allocation layer**. That is enough to justify defensive controls, not enough to justify enumeration or a published generator.

**Decision-ready insight:** Do not spend club effort guessing the digit code. Ask MUJ's registrar or application owner for a redacted codebook under authorization, then use synthetic examples to validate only the fields relevant to security testing.

## Public Exposure Map: One Confirmed Identifier Example, Many Potential Channels

Public exposure must be separated into confirmed publication, contextual exposure, and unverified hypotheses. The official FAQ is a confirmed publication because it includes the complete example in the username formula [1]. The onboarding guide is contextual exposure because it documents the registration-number field and associated personal information without, in the cited material, publishing a bulk list [2].

The guide shows why linkage matters. In addition to the register number and academic fields, onboarding covers educational qualifications, addresses, and parent or guardian information [2]. It also requires uploaded documents and a profile photograph [2], and uses a parent's mobile number for OTP verification [2]. A bare register number may be a pseudonymous identifier in isolation, but its risk increases sharply when a document, profile, or filename links it to a name, branch, contact detail, or family information.

| Public channel | Status in this review | What was actually established | Risk if future examples appear | Recommended owner action |
|---|---|---|---|---|
| Official FAQ PDFs | **Confirmed** | One full registration-number example appears inside the username formula [1] | Search engines can preserve the name-number relationship | Replace real-looking examples with unmistakably synthetic placeholders |
| Official onboarding guides | **Confirmed contextual exposure** | Registration number is MUJ-generated, non-editable, and part of a profile containing identity and academic data [2] | Documents reveal data-model relationships even without bulk records | Redact screenshots and inspect PDF text layers and metadata before release |
| Circulars, notices, merit lists, result PDFs | **Not verified** | No defensible MUJ bulk-register list was established in the reviewed results | Bulk publication could expose cohort structure and name-number mappings | Run periodic domain and search-index reviews; prefer random publication tokens |
| Public forms and shared documents | **Not verified** | No confirmed public MUJ form containing populated student numbers | Responses or prefilled links could leak identifiers | Require authentication and avoid identifiers in shareable URLs |
| LinkedIn and resumes | **Not verified** | MUJ affiliations were discoverable, but a register-number disclosure was not confirmed | A self-published number plus name could complete the username formula | Publish student guidance saying registration numbers are identifiers, not resume content |
| GitHub repositories | **Confirmed ecosystem mapping, not number leakage** | Repositories identify attendance, marks, grades, timetable, and feedback functionality [6][7] | Routes and object categories become easy to map | Keep authorization independent of route obscurity; scan commits for secrets and personal data |
| Search caches and archives | **Inference** | An indexed official PDF can be copied beyond its original location | Deletion at origin may not immediately remove cached copies | Use synthetic examples initially and request cache removal after remediation |

The public GitHub evidence is important but should not be exaggerated. SlcmPlus runs only on three specified MUJ academic pages [6], and the reviewed code performs local DOM calculations without an external transmission call [10]. Another public project describes Flutter and FastAPI components and student features such as schedules, grades, GPA, and attendance [7]. These projects demonstrate developer interest and map high-value objects, but they do not establish that MUJ endorsed the software, that production APIs are exposed, or that authorization is broken.

**Decision-ready insight:** The immediate publication problem is not a proven bulk leak. It is that an official document teaches a deterministic username formula using a realistic full identifier. Correct that example, then monitor the unverified channels rather than claiming they already contain lists.

## Threat Model: What Enumeration Could Enable

A register number is not a password, and discovering a username is not account compromise. The security concern is compositional: public identity data plus a deterministic username can lower the setup cost for later attacks. Whether those attacks work depends on response behavior, rate limiting, MFA, password reuse, reset design, and authorization.

| Stage | Confirmed input | Potential consequence | Evidence status | Boundary that stops escalation |
|---|---|---|---|---|
| 1. Identity collection | Names and MUJ affiliation may be public; one official example links a name and number [1] | Candidate identity records | Confirmed for the example only | Minimize name-number publication |
| 2. Username derivation | `name.registration-number` formula [1] | Candidate SLCM login name | Confirmed formula | Do not treat username secrecy as a control |
| 3. Account discovery | Login/reset responses might differ | Validation of whether a candidate account exists | **Unknown for MUJ; inference only** | Generic status, body, and timing behavior [12] |
| 4. Credential attack | Password relationship to Outlook identity is documented [1] | Stuffing, spraying, phishing, or reset targeting | Threat is plausible; success unverified | MFA, throttling, breached-password protection, anomaly detection |
| 5. Authenticated object access | Attendance, marks, grades, profile, documents, and family data exist [2][6] | Horizontal or role-crossing access | Object sensitivity confirmed; vulnerability not established | Per-object server-side authorization [9] |
| 6. Persistence or wider impact | Shared identity or sessions could increase blast radius | Cross-service compromise | **Inference; architecture not established** | Separate trust boundaries, session controls, conditional access, incident response |

### Username enumeration

OWASP says login, password reset, and recovery should return generic messages regardless of whether the account is wrong, nonexistent, locked, or disabled [12]. **Inference:** because MUJ's username grammar is public, discrepancies in any of those workflows would be more consequential. A secure system should make both the message and the practical response behavior resistant to account discovery. This report does not claim MUJ currently leaks that distinction.

### Credential stuffing, spraying, and phishing

OWASP distinguishes credential stuffing, password spraying, and brute force, and identifies throttling as a control against excessive guesses [12]. Credential stuffing specifically uses username/password pairs obtained from another breach [3]. **Inference:** a known username format helps attackers transform public or breached identity data into institution-specific candidate accounts. The Outlook relationship may also make social-engineering language more convincing, but it does not prove password synchronization or reuse.

MFA is the strongest compensating control in the reviewed guidance; OWASP recommends implementing it wherever possible while recognizing feasibility constraints [12]. NIST additionally requires protection against online guessing for applicable authenticators and allows lower attempt limits, progressive delays, bot detection, and adaptive signals [5]. The club should assess these controls with MUJ, not test them against students.

### IDOR and object-level authorization

OWASP describes IDOR as a missing object-level authorization check around an object reference [9]. A numeric register number is therefore neither necessary nor sufficient for an IDOR. **Inference:** the highest-value review targets are any attendance, marks, grades, profile, document, or parent-facing operations that accept a student-related key. The secure implementation derives the subject from the authenticated session or checks access to the referenced object on every request [9].

**Decision-ready insight:** Prioritize account-discovery resistance and object authorization. They are the controls that make identifier predictability harmless.

## Application-Security Review Targets From Public Evidence

The public manifest identifies three exact MUJ page categories: attendance summary, internal marks, and grades [6]. The companion script confirms that rendered tables contain attendance counts, mark components, credits, and letter grades [10]. MUJ's onboarding guide broadens the data model to identity, program, birth date, phone, email, addresses, parent or guardian details, uploaded documents, and OTP verification [2]. These are review priorities because of sensitivity, not because a defect has been shown.

| Surface | Publicly evidenced data or behavior | Defensive question for an authorized review | Finding status |
|---|---|---|---|
| Student login | Deterministic username formula and Outlook-related password guidance [1] | Are messages, status codes, timing, rate limits, and logs resistant to account discovery? | Control question; no vulnerability claimed |
| Microsoft identity path | Public OpenID metadata for `muj.manipal.edu` points to Microsoft login infrastructure [14] | Is MFA enforced appropriately, and are legacy or fallback paths governed consistently? | Identity relationship confirmed; configuration unknown |
| Attendance summary | Present, absent, total, and calculated allowance information [10] | Does every request bind the returned record to the authenticated student or authorized staff role? | Object category confirmed |
| Internal marks | Multiple mark cells and calculated totals [10] | Can only the subject student and authorized academic roles read each record? | Object category confirmed |
| Grades | Credits, letter grades, and semester GPA calculation [10] | Are grade objects protected against horizontal and vertical role crossing? | Object category confirmed |
| Student profile | Registration number, branch, DOB, gender, phone, email, admission year [2] | Are read and update permissions field-specific, logged, and rechecked on every request? | Data categories confirmed |
| Addresses and family data | Addresses and parent or guardian details [2] | Are parent, student, coordinator, admissions, and administrator roles separated by least privilege? | Data categories confirmed |
| Document upload | PDF documents, photographs, declarations, and physical verification [2] | Are upload ownership, retrieval authorization, retention, and administrative access controlled? | Workflow confirmed |
| Feedback automation | A public extension automates filling MUJ's SLCM feedback form [17] | Does the server independently enforce student eligibility, submission state, and anti-replay rules? | Automation exists; server behavior unknown |
| Third-party mobile project | Public project advertises schedules, grades, GPA, attendance, and custom student/parent authentication [7] | Are unofficial integrations prohibited from collecting production credentials, and are students warned about custody risk? | Project claim confirmed; official status unknown |

OWASP's authorization guidance says deny by default, apply least privilege horizontally and vertically, and validate permission on every request regardless of request source [11]. It also recommends automated unit and integration tests for access-control logic [11]. Those principles matter more than hiding MVC route names or replacing register numbers with GUIDs.

The supplied platform stack creates an additional governance requirement: MUJ should document the exact .NET Framework release, OS servicing status, ASP.NET MVC dependencies, IIS modules, Akamai rules, and authentication handoffs. "4.x" is too broad for a lifecycle conclusion. This report therefore does not infer patch status from the version family or claim that Akamai automatically protects origin, login, or application authorization.

**Decision-ready insight:** Build the review around trust boundaries and data ownership, not around a route-scanning exercise. A CDN, opaque ID, or hidden URL cannot compensate for missing authorization.

## Defensive Control Plan

### Priority matrix

| Priority | Control | Concrete implementation objective | Evidence/rationale | Safe verification method |
|---:|---|---|---|---|
| P0 | Remove realistic identifiers from public examples | Replace `garv.2506040062` with an unmistakably synthetic, non-routable placeholder | Official FAQ currently publishes the formula and example [1] | Document review only |
| P0 | Generic authentication and recovery behavior | Equalize messages and practical response behavior for valid, invalid, locked, and disabled accounts | OWASP enumeration guidance [12] | Synthetic known/unknown accounts in a scoped test environment |
| P0 | Per-object authorization | Check object ownership and role authorization on every read and change | OWASP IDOR and authorization guidance [9][11] | Automated positive and negative tests with synthetic students and roles |
| P0 | MFA and guessing resistance | Enforce appropriate MFA; combine account-aware limits with bot and risk signals | OWASP and NIST guidance [12][5] | Owner-observed test accounts; no production guessing |
| P1 | Data-publication governance | Scan PDFs, text layers, spreadsheets, public shares, and repository history for name-number pairs | Onboarding data model includes extensive personal information [2] | Offline content scan and approval workflow |
| P1 | Recovery-channel hardening | Ensure reset does not disclose account validity and uses verified, protected recovery factors | OWASP recovery and generic-response guidance [12] | Synthetic recovery identities |
| P1 | Role model and least privilege | Document permissions for student, parent, coordinator, admissions, academic, DMS, and administrator functions | The guide identifies several data sections and support roles [1][2] | Policy-to-test traceability matrix |
| P1 | Detection and response | Log authentication failures, lockouts, access denials, and unusual object-access patterns | OWASP recommends logging and reviewing failures and lockouts [12] | Tabletop exercise and controlled synthetic events |
| P2 | Identifier redesign | Use non-semantic public references where feasible, while retaining internal register numbers for business use | OWASP treats complex random identifiers as defense in depth, not primary access control [9] | Architecture review and migration test |
| P2 | Unofficial-client policy | Warn students against entering MUJ credentials into unapproved apps; define an approved integration model | Public projects advertise access to sensitive academic functions [7] | Communications review and sanctioned-app inventory |

### Safe validation protocol

1. **Written authorization:** MUJ should define hosts, test dates, allowed workflows, source addresses, data-handling rules, and emergency contacts. Production student accounts and records remain out of scope.
2. **Synthetic identities:** MUJ creates test students in at least two programs and two roles, plus a nonexistent control identity. The application owner, not the club, chooses identifiers.
3. **No enumeration:** Tests compare only the finite, preapproved identities. Researchers do not derive or try neighboring numbers.
4. **Authorization matrix:** For each sensitive object type, test owner access, peer denial, parent boundary, staff boundary, and unauthenticated denial. OWASP says permissions must be validated on every request [11].
5. **Recovery checks:** Compare preapproved existing and nonexistent test accounts for equivalent public behavior. Do not send recovery traffic to real students.
6. **Rate-control checks:** Use a small owner-approved script or test harness against a staging environment only. Validate delay, blocking, alerting, and recovery without testing real passwords.
7. **Evidence minimization:** Capture request IDs, timestamps, and synthetic identifiers rather than personal records. Do not include live cookies, tokens, documents, or credentials in club reports.
8. **Coordinated reporting:** Report control failures privately to MUJ with reproduction limited to synthetic accounts, impact analysis, remediation, and retest criteria.

The Indian Digital Personal Data Protection Act states that digital personal data processing must recognize both individuals' protection rights and lawful processing needs [13]. This report is not legal advice. As a prudent governance position, MUJ should treat a register number linked to a name, academic record, contact detail, or family information as personal data and minimize its public dissemination.

**Decision-ready insight:** The P0 controls make register-number predictability largely non-exploitable. Identifier redesign is useful, but only after authentication, recovery, and authorization are correct.

## Synthesis: Syntax, Identity, and Authorization Must Be Separated

The evidence supports three distinct layers that should not be collapsed.

| Dimension | Register-number syntax | Account identity | Academic-object authorization |
|---|---|---|---|
| Confirmed mechanism | Ten-digit example generated by MUJ [1][2] | `name.registration-number` username and Outlook-related guidance [1] | Sensitive attendance, marks, grades, profile, document, and family objects exist [2][6] |
| Main uncertainty | Meaning of digit groups and neighbor validity | Whether public workflows reveal account existence; MFA and rate-control configuration | Whether any endpoint accepts another student's identifier or misses a role check |
| Security failure mode | Overexposure or semantic predictability | Enumeration, stuffing, spraying, phishing, recovery abuse | Horizontal or vertical unauthorized access |
| Best control | Publication minimization and, secondarily, non-semantic public references | Generic responses, MFA, throttling, detection, secure recovery | Deny by default and check every object's authorization on every request |
| Evidence base | One authoritative full example | Direct official username formula | Public routes and data categories, but no demonstrated defect |
| Confidence | Medium for structure, low for semantics | High for derivation, unknown for exploitability | High for sensitivity, low for vulnerability existence |

The non-obvious tension is that decoding the ten digits is not necessary for the most important risk. The official formula already reveals how a known number becomes a username [1]. Even if every digit after `25` were random, an exposed name-number pair would still expose the login identifier. Conversely, even a perfectly sequential register-number scheme would be of limited security consequence if login and recovery did not reveal account validity, MFA resisted password compromise, and every academic object was bound to the authenticated subject.

A second tension concerns opaque identifiers. OWASP recommends complex, random identifiers as defense in depth but explicitly retains server-side access checks as essential [9]. Therefore, changing `2506040062` to a UUID without fixing authorization would reduce guessability while preserving the underlying defect. The proper sequence is: fix authorization, authentication, and recovery first; then reduce public semantic leakage.

A third tension concerns public student tools. SlcmPlus demonstrates that useful analytics can be calculated locally from a student's rendered page without external transmission [10]. In contrast, a separate mobile project advertises custom authentication and a backend architecture [7]. **Inference:** MUJ can support student innovation more safely through documented, scoped, token-based interfaces or approved client-side extensions than by leaving students to entrust credentials to unofficial backends.

Finally, the wider Manipal ecosystem can mislead researchers. Code targeting `slcm.manipal.edu` is not evidence about MUJ Jaipur's host [15]. A disciplined assessment must preserve entity, host, and application boundaries.

**Decision-ready insight:** Treat the register number as a public identifier, the username formula as known, and authorization as the security boundary. That model remains safe even if the digit scheme later proves fully predictable.

## VERDICT

**Overall verdict: MATERIAL DEFENSIVE EXPOSURE, BUT NO VERIFIED ENUMERATION OR IDOR VULNERABILITY.**

| Proposition | Verdict | Confidence | Reason |
|---|---|---:|---|
| MUJ SLCM usernames incorporate the registration number | **Confirmed** | High | Official FAQ gives the exact formula and example [1] |
| The ten-digit value encodes batch, campus, stream, and sequence in the proposed positions | **Not established** | Low | No official legend and only one authoritative exemplar |
| `25` is the admission year | **Inference only** | Low | Plausible appearance, but not corroborated |
| `0062` is a sequential student counter | **Inference only** | Low | Zero padding suggests it, but no neighboring official examples were verified |
| Public PDFs expose at least one complete example | **Confirmed** | High | Official FAQ [1] |
| Public circulars, result lists, or LinkedIn currently expose bulk MUJ numbers | **Not established in this review** | Low | No defensible bulk source was verified |
| Predictable username derivation can aid account targeting | **Supported inference** | Medium-high | Formula is confirmed; exploitability depends on live controls |
| MUJ has an IDOR on attendance, marks, grades, profile, or documents | **Not established** | Very low | Sensitive objects are documented, but no authorization failure was tested or observed |
| MUJ should prioritize generic responses, MFA, rate controls, logging, and object-level authorization | **Strong recommendation** | High | Directly aligned with OWASP and NIST guidance [12][9][5][11] |

**Confidence level: HIGH for the documented username formula and data categories; MEDIUM for the resulting threat model; LOW for any proposed digit-field decoder; VERY LOW for claims of an existing exploitable vulnerability.**

The university security club can responsibly report that MUJ has made the username construction and a realistic identifier example public. It should not report that the number scheme has been decoded, that accounts can be enumerated, or that an IDOR exists. The proper next step is a coordinated, synthetic-account assessment with MUJ's written authorization.
